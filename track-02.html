02 · 架构与版本工程

目标版本的分支策略、补丁清单和多仓库依赖是否锁定？没有版本工程，就没有可长期服务的产品。

第 3–4 周能力线

控制面：意图如何到芯片

分布式控制面核心在 Redis 多实例与管道：管理接口对 CONFIG_DB（如 Redis DB 4）的写入触发 OrchAgent 监听；OrchAgent（sonic-swss）把 VLAN、BGP 等意图转成 SAI 对象，经 ASIC_DB 下发到 syncd。产品化时要能回答：配置从哪进、状态从哪出、失败卡在哪一环、如何取证。

多仓库依赖怎么进物料清单

仓库 / 组件角色版本工程要锁什么
sonic-buildimage镜像组装分支、构建参数、产物哈希
sonic-swssOrchAgent 等与 SAI/平台插件的兼容版本
sonic-sairedis / syncdSAI 实现与下发SAI 头文件与厂商库版本
sonic-utilities运维命令与镜像同版本发布
平台插件 / BSP板卡适配板卡版本 ↔ 插件版本矩阵

分支与发布节奏

  • 社区基线 → 平台插件 → 目标镜像的依赖链要与发布节奏对齐，避免「插件已升、镜像未跟」。
  • 补丁物料清单（BOM）：每个补丁的来源 PR、优先级、冲突风险、回退方式。
  • 升级与回退必须写进版本定义：失败恢复步骤、数据保全、时间窗口。

公开架构图怎么用（和不能怎么用）

公开架构图与流程可以成为验证问题的输入（例如：遥测挂哪个库、重启哪个容器影响业务），但不能绕过版本和平台门禁。问「这张图对应的版本号与板卡是什么」，而不是「图画得很全所以支持」。

核对问题

  1. 目标 release 的分支策略是什么？与上游同步周期？
  2. patch BOM 是否锁定？谁负责合并冲突？
  3. 多仓依赖进入 BOM 的机制是手工还是流水线？
  4. 升级失败时回退到哪一版？谁演练过？

本阶段产出

  • 分支与发布节奏图。
  • 补丁物料清单。
  • 升级/回退策略一页纸。

动手任务验收标准

  • 能口述控制面主链并指出取证点
  • 补丁物料清单覆盖当前目标 release
  • 升级/回退策略一页纸含演练记录引用

自测题（点击展开答案）

自测 1：用户配置写入 CONFIG_DB 后，到芯片大致经过哪些环节？
CONFIG_DB → OrchAgent（sonic-swss）转 SAI 对象 → ASIC_DB → syncd 执行 → ASIC。
自测 2：patch BOM 为什么要锁？
避免镜像、插件、多仓依赖版本漂移导致现场不可复现、无法回退或责任不清。
自测 3：公开架构图能否绕过版本门禁？
不能。架构图只能用来提验证问题；结论仍须绑定版本、板卡与证据。

建议：正确率 ≥ 80% 再进入下一页。培训组织者可按此判分。
